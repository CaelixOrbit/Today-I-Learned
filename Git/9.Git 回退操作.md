# Git 回退操作

## 撤销未提交的修改

当文件在工作区或暂存区发生了修改，但尚未执行 `git commit` 时，可以使用以下命令将状态复原。

> [!NOTE]
> 
> 自 Git 2.23 版本起，官方引入了专用的 `git restore` 命令来处理工作区和暂存区的撤销，以剥离原本 `git checkout` 过于复杂的职责。

- **撤销工作区修改**：

  ```bash
  # 丢弃工作区指定文件的修改（使其恢复到最后一次提交或暂存的状态）
  git restore <file-name>
  
  # 丢弃工作区所有文件的修改
  git restore .
  
  # （传统方式）使用 checkout 丢弃工作区修改
  git checkout -- <file-name>
  ```

- **撤销暂存区修改**：

  ```bash
  # 将指定文件移出暂存区（但保留工作区的修改内容）
  git restore --staged <file-name>
  
  # 将所有文件移出暂存区
  git restore --staged .
  
  # （传统方式）使用 reset 移出暂存区
  git reset HEAD <file-name>
  ```

> [!CAUTION]
> 
> 撤销工作区修改会永久丢弃本地未提交的代码，无法找回！

## 贮藏未提交的修改

贮藏功能可以将工作目录的脏状态（包括已跟踪文件的修改和已暂存的改动）压入一个栈中保存，使工作目录恢复干净（即未修改的状态），从而支持自由切换分支。存入栈中的改动可随时取出并重新应用。

- **保存贮藏**：

  将工作区和暂存区中已跟踪文件的改动压入栈中，使当前分支恢复到干净状态。

  ```bash
  # 保存当前进度（推荐使用 push 替代旧版的 save）
  git stash push
  # 简写形式 git stash
  
  # 保存进度并添加贮藏说明
  git stash push -m "<message>"
  ```

- **常用附加选项**：

  ```bash
  # 贮藏时包含 "未跟踪（Untracked）" 的新文件
  git stash -u
  # 或 git stash --include-untracked
  
  # 贮藏工作区和暂存区的更改，但暂存区维持不变
  git stash --keep-index
  
  # 交互式贮藏：Git 会逐个代码块询问你是否需要贮藏
  git stash --patch
  ```

- **查看贮藏**：

  查看当前栈中所有的贮藏记录。

  ```bash
  git stash list
  ```

  输出示例：`stash@{<n>}: <message>`，其中 `n` 是最新一次保存的贮藏索引。

- **应用贮藏**：

  将栈中的改动重新应用到当前工作目录（可以是不同于保存时的分支）。

  ```bash
  # 重新应用最近一次的改动（默认 stash@{0}），应用后其仍然保留在栈中
  git stash apply
  
  # 重新应用指定的贮藏记录
  git stash apply "stash@{<n>}"
  
  # 重新应用最近一次的改动，并将其从栈中丢弃（最常用）
  git stash pop
  ```

  默认情况下，`apply` 或 `pop` 只会恢复文件的修改内容，原本处于已暂存状态的文件恢复后会变成已修改未暂存状态。若需尝试恢复暂存状态，需附加 `--index` 选项。

- **贮藏冲突**：

  如果贮藏中的修改与现有内容在同一文件的同一位置发生了不同步的更改，应用贮藏时 Git 就会报告合并冲突。

  冲突的处理逻辑与普通的分支合并冲突一致。只是最后不需要执行 `git commit`。

- **删除贮藏**：

  ```bash
  # 移除栈中特定的贮藏记录
  git stash drop "stash@{<n>}"
  
  # 清空整个贮藏栈
  git stash clear
  ```

- **基于贮藏创建分支**：

  如果将工作贮藏了一段时间，原分支可能已经发生了许多提交。此时直接 `apply` 可能会引发合并冲突。可以使用以下命令，基于贮藏保存时的状态创建一个新分支并应用改动：

  ```bash
  # 创建新分支，检出贮藏时的历史节点，应用修改，并丢弃该贮藏记录
  git stash branch <new-branch-name> "[stash@{<n>}]"
  ```

## 修改最新提交

若最新一次提交存在文件遗漏，或者提交说明有误，可执行追加修改操作以覆写该次提交。

```bash
# 仅修改最新一次的提交说明信息（不改变文件内容）
git commit --amend -m "<new-message>"

# 将遗漏的文件追加到最新提交中，且不修改原来的提交说明
git add <forgotten-file-name>
git commit --amend --no-edit
```

`--amend` 选项会将当前暂存区的内容与最新提交的内容进行整合，生成一个新的提交对象来替换掉原来的最新提交（哈希值会改变）。

对于在最新提交后又被修改并添加到暂存区的文件，新提交将直接采用暂存区中的最新版本。这个过程是直接覆盖替换，不会触发常规的合并冲突机制。

`--no-edit` 选项表示不修改提交说明。

> [!CAUTION]
> 
> `--amend` 本质上是重写了历史记录，因此不建议在已经推送到远程仓库的提交上使用。

## 回退历史提交

如果需要对更早的历史记录进行回退，Git 提供了两种截然不同的策略：`git reset`（重置指针）和 `git revert`（反向提交）。

### 使用 `git reset` 重置分支指针

`reset` 会直接将当前分支的 HEAD 指针强行向后移动到指定的历史提交，从而 "抹除" 之后的提交记录。它常用于本地私有分支的后悔操作。

根据对工作区和暂存区的影响，`reset` 分为三种模式：

```bash
# 【软重置】：仅移动 HEAD 指针。被 "抹除" 的提交差异会被放回暂存区，工作区不变。
git reset --soft <commit-hash>

# 【混合重置】（默认行为）：移动 HEAD 指针，重置暂存区。差异会退回到工作区等待重新处理。
git reset <commit-hash>
git reset --mixed <commit-hash>

# 【硬重置】：移动 HEAD 指针，并清空暂存区和工作区。（极其危险，会丢失所有修改！）
git reset --hard <commit-hash>
```

`git reset` 还可以对特定的文件进行重置（对文件仅支持混合重置）。此时 Git 不会改变 HEAD 指针的指向，而是将指定文件在暂存区中的状态，重置为目标提交 `<commit-hash>` 中的版本（工作区内容保持不变）。

```bash
# 将指定文件在暂存区的状态重置为某个历史提交的版本（不移动 HEAD 指针）
git reset <commit-hash> <file-name>
```

### 使用 `git revert` 创建反向提交

`revert` 不会移动指针，也不会抹除历史。相反，它会计算出指定提交的 "相反内容"，然后创建一个全新的提交加在时间线最前端，用来抵消掉之前的修改。由于它保留原有历史，通常是共享团队分支上回退代码的推荐方式。

```bash
# 撤销指定的单次提交（生成一个相反的新提交）
git revert <commit-hash>

# 撤销最新提交
git revert HEAD

# 撤销一段区间内的所有提交（生成一系列相反的新提交）
git revert <old-commit-hash>..<new-commit-hash>
```

**`reset` vs `revert` 对比：**

| 维度         | `git reset`（重置）              | `git revert`（反转）       |
| :----------- | :------------------------------- | :------------------------- |
| **历史记录** | 重写/抹除历史                    | 保留历史，向前添加新提交   |
| **安全性**   | 危险（配合 `--hard` 会丢失数据） | 安全（不丢失任何原有数据） |
| **适用场景** | 本地分支、未推送的提交           | 共享分支、已推送的提交     |

## 彻底从历史中擦除文件

如果误将敏感信息或大体积文件提交到了仓库，由于快照机制，它会永远存在于历史记录中。

一种做法是使用 `filter-branch` 遍历历史，并配合 `--tree-filter` 选项，在检出项目的每一个提交后运行指定的命令并重新提交结果，从而擦除整个提交历史：

```bash
# 遍历从最初起点到当前 HEAD 的所有历史，强制删除指定文件
git filter-branch --tree-filter 'rm -f <file-name>' HEAD
```

> [!NOTE]
> 
> `filter-branch` 执行极慢且存在潜在风险，因此在现代大型 Git 仓库中，官方更推荐使用外部第三方工具 `git-filter-repo` 进行历史清洗。

## 引用日志

`git reflog` 用于显示本地仓库中 HEAD 指针的所有移动轨迹。

即使是执行了 `reset --hard` 被抹除的提交，或已被删除的分支，只要其记录尚未被 Git 的垃圾回收机制清除，均可通过 `reflog` 找回。

```bash
# 查看本地 HEAD 的更新记录（包括 reset、checkout、commit 等）
git reflog

# 查看本地所有引用的更新记录
git reflog --all

# 找到误操作前的哈希值，强行将指针重置回去
git reset --hard <target-commit-hash>
```

引用日志是完全本地化的。它仅记录当前仓库的操作轨迹，不会随克隆或推送而同步。因此，不同克隆仓库的引用日志互不相同，且新克隆的仓库引用日志初始为空。
